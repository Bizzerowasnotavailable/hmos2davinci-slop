Every folder in `patches/` is one patch: `patch.json` describes what it adds to the images, `files/` holds
its binaries (sources in `src/`), an optional `hook.py` edits files taken from the OTA itself.
Generated by `tools/gen_patch_docs.py`.

## 15-no-crash-reboot

**No reboot when a service crashes**

HarmonyOS reboots the phone when SceneBoard crashes 4 times in 4 minutes, and init reboots it when a 'critical' service (render_service, foundation, samgr, ...) keeps crashing: it first stops every service and unmounts /data, so with the kernel refusing the reboot the phone is left dead. On a port a missing driver is enough to trigger this. The SceneBoard policy is switched off and the critical flag is cleared for every system and vendor service (system ones are re-declared in /vendor, system.img is not rebuilt): crashed services are simply restarted.

init commands:

- `param:bootevent.boot.completed=true: stop watchdog_service`
- `boot: stop watchdog_service`
- `pre-init: mount none /vendor/etc/sweet/ams_service_config.json /system/etc/ams_service_config.json bind`

Hook: `hook.py` (edits files taken from the OTA).


## 16-performance

**Smoother UI (GPU at full speed)**

Keeps the Adreno 618 at its maximum clock after boot (performance governor) and makes schedutil react faster. render_service composes the whole screen on the GPU, so this removes most of the stutter at the cost of some battery.

init commands:

- `param:bootevent.boot.completed=true: write /sys/class/kgsl/kgsl-3d0/devfreq/governor performance`
- `param:bootevent.boot.completed=true: write /sys/class/kgsl/kgsl-3d0/idle_timer 1000`
- `param:bootevent.boot.completed=true: write /sys/devices/system/cpu/cpu0/cpufreq/schedutil/up_rate_limit_us 500`
- `param:bootevent.boot.completed=true: write /sys/devices/system/cpu/cpu6/cpufreq/schedutil/up_rate_limit_us 500`
- `param:bootevent.boot.completed=true: write /sys/devices/system/cpu/cpu0/cpufreq/schedutil/down_rate_limit_us 20000`

## 46-pin-lock

**PIN / password lock screen without TEE**

Huawei's user_auth and pin_auth HDI services keep credentials in their TEE (iTrustee), which sweet does not have: a PIN could be set but the lock screen stayed swipe-only. They are replaced by OpenHarmony's own REE implementation (drivers_peripheral user_auth 3.0 / pin_auth 2.1, OpenHarmony-5.1.0-Release, Apache-2.0), which keeps the PIN data salted and hashed in /data/service/el1/public/{pinauth,userauth}. The user_auth service is built against the OpenHarmony 5.0 IDL of user_auth v3.0, the one HarmonyOS 5.x uses (no VerifyAuthToken): with the 5.1 IDL Huawei's stub called the wrong methods and the lock screen asked for a PIN that was never set.

Files added to /vendor:

## 47-camera

**Camera (Android CamX HAL through a bridge) - EXPERIMENTAL**

sweet's camera sensors, ISP and JPEG encoder only work through Qualcomm's Android camera HAL (CamX, camera.qcom.so). sweetcam-launch runs it in a private mount namespace that looks like a minimal Android (/system, /vendor, /apex from /vendor/android, an Android property area) inside cambridge, a small bionic program that drives the camera3 HAL and hands the frames over a unix socket. sweet_camera_host implements the OpenHarmony camera HDI (v1.0), registers camera_service with the HDF service manager like Huawei's CameraDaemon and copies the frames into the apps' buffer queues (preview NV21/NV12, JPEG photos).
